# ADR-0011: WiFi scan для автозаполнения SSID

## Статус
Принято.

## Контекст
Форма provisioning требует ввода SSID вручную. Для удобства и для демонстрации
«выбрал сеть — ввёл пароль» нужен список доступных сетей с возможностью выбора.

## Решение
Эндпоинт `GET /api/scan` (без токена, только AP) возвращает JSON-массив:
`[{"ssid":"...","rssi":-45,"auth":"wpa2"}, ...]`. Отсортирован по RSSI убыв.

На captive-странице — `<select>` со списком SSID и кнопка «Обновить скан».
Выбор сети заполняет поле SSID в provisioning-форме.

**Архитектурное следствие:** `esp_wifi_scan_start()` требует запущенного
STA-интерфейса. В чистом AP-режиме скан невозможен. Значит, в режиме
провижининга/демо устройство работает в **APSTA**, а не AP. При переходе в
STA после успешного provisioning — AP гасится, устройство остаётся в STA
(как в ADR-0004).

Уточнение к ADR-0004: «fallback в AP» означает «fallback в APSTA, если нужен
скан, иначе AP». Для базового демо и provisioning — APSTA.

## Альтернативы
- Ручной ввод SSID без скана: работает, но ухудшает демонстрацию и добавляет
  опечатки при настройке.
- Скан только по кнопке, без автообновления: выбрано — скан по кнопке, чтобы
  не нагружать радио и не мешать соединению.

## Последствия
+ UI провижининга удобнее, демонстрация выигрывает.
+ AP-режим становится APSTA: чуть больше памяти и энергии, для USB-питания
  неважно.
− Скан занимает ~2–4 секунды, на это время captive-страница должна показывать
  индикатор загрузки.
− Добавлен эндпоинт и компонентная зависимость: `wifi_mgr` теперь отвечает
  и за скан, `http_api` — за его JSON-обёртку.
− ADR-0004 дополняется: в режиме провижининга — APSTA.
