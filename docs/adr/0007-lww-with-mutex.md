# ADR-0007: Last-writer-wins с мьютексом вокруг состояния

## Статус
Принято.

## Контекст
Два источника команд — физическая кнопка (задача button) и HTTP-обработчик
(задача httpd) — могут одновременно изменить состояние реле. Нужно определить
и семантику конфликта, и механизм синхронизации.

## Решение
Семантика: last-writer-wins — побеждает команда, применённая последней.
Механизм: единственный мьютекс вокруг логического состояния и записи GPIO.
Все источники захватывают мьютекс на время «чтение — изменение — запись».
Очередь команд и отдельная задача-владелец реле не вводятся.

Логическое состояние — источник истины (переменная под мьютексом), а не чтение
пина. Физическое положение контакта может кратковременно расходиться
с логическим (дребезг, задержка GPIO); это нормально.

## Альтернативы
- Очередь команд + задача-владелец: детерминированный порядок и удобная точка
  логирования, но больше кода и сущностей. Станет актуально при добавлении
  таймеров/расписаний — тогда это будет ЗАМЕНА этого ADR, а не тихое изменение.
- Без синхронизации: возможны data race, двойное переключение GPIO с
  непредсказуемым итогом. Отвергнуто.

## Последствия
+ Нет гонок данных, минимум кода.
+ Порядок применения команд = порядок захвата мьютекса.
− Нет буферизации: при шторме команд возможны «лишние» переключения реле
  (каждое применение — физический щелчок). Для одного канала и ручного
  управления приемлемо.
− При добавлении расписаний потребуется пересмотр.
